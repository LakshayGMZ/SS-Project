RECORD-LOCKING TRANSACTION FLOW

1. A request identifies the table and record ID it will read or change.
2. The database computes that fixed-width record's byte offset and obtains a shared or exclusive fcntl byte-range lock. A process-local mutex protects same-record threads.
3. Related records are locked in a consistent order and kept locked through validation and commit.
4. Multi-record changes are written to a durable WAL, applied to the relevant table rows, and fsynced before locks are released.
5. On restart, a complete pending WAL is replayed idempotently.

Append allocation uses a separate per-table append lock because a new row has no existing record ID to lock yet. Ordinary reads and updates use only their selected row ranges; there is no whole-table lock around every request.
